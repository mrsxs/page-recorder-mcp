# page-recorder：先摸清接口，再在页面里改参数请求

录制脚本的接口都在用户自己已登录的浏览器里执行，有两种发法：

- **直接请求**（`call_api`，或 `<脚本>__<接口>` 工具）：不操作页面，在开着的那个页面里按你给的参数发请求，带浏览器 Cookie，签名、令牌类请求头用页面最近一次请求同一接口时的值（结果里 `liveHeaders` 列出用了哪些，`omittedHeaders` 列出没补上的）。快，参数随便改。
- **页面自己发**（`run_recording`，`mode: "ui"`）：回放录制的页面操作，页面自己组请求、现算签名。`api_params` 在请求发出前改接口参数，`params` 改页面上的控件，写法见 `paramHelp`：单选和下拉填已有选项，复选框填 `true` / `false`，多选传已有选项组成的数组。慢，签名一定有效。

`run_recording` 不传 `mode` 时会先直接请求、被拒就整段回放，并且之后一天都走回放（写接口只有 401 / 403 或没发出去时才自动回放）。按下面的步骤明确传 `mode`，每一步都由你决定用哪种发法。

## 1. 摸清接口

1. `list_recordings` 找到脚本。脚本库大时它只给概要，接口也不会逐个列成工具：用 `search_apis` 按关键词找接口，拿返回的 `recording_id` 和 `api` 去 `call_api`。
2. `get_recording`：内容多时返回概要（步骤、参数、接口目录 `apis[i]`）和 `result_id`。
3. 对目录里像数据来源的接口，用 `read_result`（`path: "apis[i]"`，`fields: ["url","description","params","paramNotes","responseSchema","responseSample"]`）逐个看。

完成标准：能写出这三件事，写不出就接着看接口——
- 要的数据来自哪个接口（`fn`）；
- 要改哪些参数、合法取值（日期格式、分页、排序、店铺 / 站点 id 等）；
- 返回里数据所在路径、要哪些字段、总数在哪（之后当 `result_path` / `result_fields` 用）。

接口还没有说明（`description` 为空、`fn` 是自动起的名）时，用 `save_api_docs` 把这三件事写回，下次就能按语义名直接调用。

## 2. 在页面里改参数直接请求

用 `call_api`（或这个接口自己的工具）带改好的参数，同时带 `result_path` / `result_fields` 只取要的部分。先请求一小页，确认结构和第 1 步的判断一致，再拉全量：能调大 `pageSize` 就调大，否则按分页字段逐页请求。

返回正常、业务码和录制时一致：之后换参数都这样直接请求。

## 3. 失败时按状态处理

结果里有 `next` 时直接照着调（`next.tool` 是工具名，`next.args` 是参数），不要自己拼地址、签名或改用别的办法。

这些情况扩展已经自己处理了，不用你管：
- 字段的值是别的接口发放的（票据、带令牌的地址）：先调那个接口拿新值，结果里 `chained` 列出用了哪些。
- 接口带页面每次现算的反爬串（拼多多 `anti-content` / `crawlerInfo` 这类，结果里 `pageGenerated`）：不发旧值，只重做发出它的那一步、让页面自己发（结果里 `via: "page"`、`trigger`）。不要从录制里抄这些串，也不要自己算。
- 页面地址带会过期的参数（令牌、签名、时间戳）：打开时用开着的同一页面现在的地址、录制时来源页上指向它的链接，或去掉这些参数（结果里 `page` / `startPage`）。`warnings` 说起始页跳走了、或报错提示起始页拒绝了请求时：用户手上有这个页面的新链接（邮件、聊天里的），让用户给你，`run_recording` 传 `start_url` 重跑；没有就转告用户从来源页重新录制。

其余从上往下，按第一条命中的处理：

| 结果 | 含义 | 下一步 |
|---|---|---|
| `unknown: true`，或 5xx / 408 / 429 | 结果未知，服务端可能已经处理 | 先查询确认结果。查询类接口可以稍后重试，提交类接口确认没生效后才重发 |
| `reason: "page_generated_fields_required"`，或 `via: "page"` 失败 | 要页面现算反爬串，只重做一步没拿到 | 照 `next` 调 `run_recording`（`mode: "ui"`）；`next.note` 说改写也被拒时，改用 `params` 改页面上的控件 |
| `notSent: true` | 请求没发出 | 按 `error` 补参数，或走下面的「让页面自己发」 |
| `writeRejected: true` | 写接口返回失败，说不准有没有生效 | 先查询确认，确认没生效后才走「让页面自己发」 |
| 401 / 403，且有 `omittedHeaders` | 页面最近没发过这些鉴权头 | 走「让页面自己发」的第 1、2 步，拿到最新的头 |
| 其余 401 / 403 | 服务端拒绝了鉴权，请求没生效 | 走「让页面自己发」 |
| `rejected: true`，或业务返回码和录制时不同（错误里常见 sign、签名、token、风控） | 服务端返回失败，常见原因是要页面现算签名 | 查询类接口走「让页面自己发」；提交类接口先查询确认没生效，再走「让页面自己发」 |

### 让页面自己发

1. **页面发一次**：`run_recording`，`mode: "ui"`，`api_params` 写上这次要改的参数（键是接口目录里的 `name`，按 `query` / `body` / `path` 分），例如 `{"POST /sbn/new_goods/get_skc_diagnose_list": {"body": {"pageIndex": 2}}}`，复用开着的标签页（不传 `new_tab`）。页面自己发请求、按你的参数改写，结果里就有数据；同时那个页面记下了最新的签名头。
2. **同一页面再直接请求**：紧接着换个参数 `call_api` 一次。通过：签名能复用一段时间，回到第 2 步的做法，过期被拒时再做一次第 1 步。
3. **签名每次现算**：还被拒，就每次都让页面自己发——
   - 改 `api_params` 的结果正确：每次换参数都用 `run_recording` + `mode: "ui"` + `api_params`；
   - 改 `api_params` 也被拒（签名覆盖了参数）：用 `params` 改页面上的控件，让页面按新条件组请求；要改的条件不在 `params` 里时，告诉用户要重新录制哪个操作。
4. **写回结论**：用 `save_api_docs` 把这个接口的请求方式写进它的 `description`，例如「要页面现算签名，直接请求 403；用 run_recording mode=ui + api_params 改 pageIndex / pageSize」。下次按结论直接选发法。

## 把几条脚本合成一条

用户把一个流程分成几条录（登录、搜索、导出……），要合成一条时：

1. 每条都 `get_recording`，看起始页面和步骤列表。
2. 排顺序：登录、切换店铺放最前；前一条拿到的数据（订单号、搜索结果）是后一条的输入时，前一条在前；用户说了顺序就照用户的。拿不准时把排好的顺序和理由告诉用户确认，再合并。
3. 找要截掉的步骤：后面几条开头重复的打开首页、登录，用这一段的 `from_step` 截掉（步骤号就是 `get_recording` 里的编号，含两端）。
4. `merge_recordings`，`parts` 按执行顺序排，带上 `name`。原来的脚本不动，返回新脚本的 id、步骤和参数。
5. 核对返回的步骤顺序；参数里出现「_第N次」说明几段用了同一个输入框，告诉用户回放时各填哪个。再用 `save_api_docs` 写说明。

## 结果太大

调用时带 `result_path` / `result_fields` / `result_limit`；拿到 `result_id` 后用 `read_result` 翻页、换字段，不会重复请求接口。`result_id` 保留最近 30 次、30 分钟内的结果，MCP 进程重启后失效（有的 AI 工具每条消息都重启）。失效后，查询类接口重新调用并直接带 `result_path`，提交类接口先确认能重复执行。
